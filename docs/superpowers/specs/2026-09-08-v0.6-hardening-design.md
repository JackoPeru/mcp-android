# MCP Android v0.6 Hardening Design

## Goal

Harden the existing MCP Android implementation for autonomous use by Codex/Hermes without changing the core trust model: private Tailscale transport, explicit user grants, no root/ADB requirement for standard features, and optional Termux/Shizuku backends.

## Scope

This pass improves four areas that are already implemented:

1. update/release supply-chain safety;
2. request concurrency and timeout reliability;
3. Android foreground-service recovery after Tailscale interruptions;
4. diagnostics exposed through the existing status surface.

No new broad device-control capability is added in this pass.

## Existing work preserved

The branch starts with uncommitted v0.6.1 updater/versioning changes already present in the workspace. They are treated as baseline work, not discarded or rewritten without cause. They already pass the current Node and Android verification suites.

## Update and release trust

The updater continues to use GitHub stable releases and SHA-256 sidecars, but it must validate the APK itself before presenting Android's install UI:

- package name must equal `com.example.androidmcp`;
- APK versionName must equal the release semantic version;
- candidate versionCode must be greater than the currently installed versionCode;
- candidate signer certificate digest set must equal the installed app signer digest set.

Android PackageInstaller remains the final platform verifier, but MCP Android rejects an invalid candidate before creating an install session.

Release publication becomes immutable:

- an existing release tag is an error, never overwritten with `--clobber`;
- workflow-dispatched releases must run from `main`;
- release tag must equal `v<package.json version>`;
- local publishing must require a clean `main` checkout that is synchronized with `origin/main`.

## RPC concurrency and deadlines

The current implicit `method.startsWith("file_")` / "everything else is UI" lock classification is replaced by an explicit policy:

- FILE: all `file_*` methods, one at a time;
- SHELL: `shell` and `shizuku_shell`, one privileged execution at a time;
- UI: gesture/UI/system actions that can conflict with each other;
- NONE: status/diagnostic/event waits that must not block UI.

`events_wait` must never hold the UI lock. Shell execution must not block UI gestures.

Transport timeouts are separated:

- socket I/O timeout protects against slow/malformed clients;
- request deadline is longer than the maximum 12-second long-poll/shell duration;
- PC bridge timeout has additional headroom beyond the phone-side request deadline.

Timeout errors continue to be treated as outcome-unknown for actions that may already have executed.

## Tailscale recovery

The foreground service remains user-started and visible. A temporary Tailscale loss no longer kills the service immediately.

The service probes the Tailscale address periodically and applies one of four actions:

- KEEP: server is bound to the current Tailscale address;
- STOP_AND_WAIT: VPN disappeared while server was running;
- START: VPN returned while server is stopped;
- RESTART: VPN address changed.

During recovery the foreground service stays alive, exposes a reconnecting state locally, and retries automatically. Explicit STOP still stops recovery and disconnects Shizuku.

## Diagnostics

The existing `android_status` response is extended rather than creating a new diagnostic tool. It reports:

- service state: running / reconnecting / stopped;
- server active request count;
- server queued request count;
- request timeout configuration;
- last service error/recovery message.

No token, document URI, shell command, clipboard content or notification body is logged or returned as diagnostic metadata.

## Testing

New logic is isolated into pure-Java helpers where practical so JVM unit tests can cover:

- APK identity/signer policy;
- RPC lock-domain classification;
- request deadline behavior;
- network recovery state transitions.

Existing Node protocol tests, Android JVM tests, lint and APK build remain required. Release scripts/workflows receive deterministic preflight checks and are inspected by the version consistency script.

## Non-goals

- no silent app installation;
- no background boot receiver;
- no public HTTP endpoint;
- no automatic Shizuku privilege escalation;
- no removal of Android user confirmation for updates;
- no broad refactor of the 47 existing MCP tools.
