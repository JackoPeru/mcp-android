# MCP Android v0.7 Agent Loop Design

## Goal

Turn MCP Android from a broad collection of device-control tools into an agent-native Android control runtime optimized for fast, reliable autonomous loops.

The core loop becomes:

```text
observe -> decide -> act_and_observe -> decide -> flow
```

instead of repeatedly paying for:

```text
ui_tree -> find -> click -> wait -> ui_tree -> find -> click -> ...
```

The project remains on-device-first:

- AccessibilityService and Android APIs for normal UI/system control;
- SAF for user-authorized files;
- NotificationListenerService for notifications/media;
- Shizuku and Termux as optional explicit backends;
- ADB only as a future optional capability backend, never a normal dependency.

## Research baseline

The design borrows proven ideas from public Android/mobile MCP projects without copying their architecture wholesale.

### NeuralBridge

Useful ideas:

- direct on-device AccessibilityService execution;
- selector-first interaction;
- event streaming;
- semantic resolution;
- scroll-to-element;
- accessibility audit;
- screenshot diff;
- token optimization.

This validates MCP Android's existing on-device-first direction and motivates state-aware observation rather than ADB-first control.

Source:
https://github.com/dondetir/NeuralBridge_mcp

### FlashZ adb-mcp

Useful ideas:

- named, structured operations instead of generic shell by default;
- JSON results rather than raw terminal output;
- guarded destructive operations;
- explicit opt-in shell escape hatch;
- rich app lifecycle, package, activity, log and device diagnostics.

Source:
https://github.com/FlashZ/adb-mcp

### Mobile Device MCP

Useful ideas:

- flattened UI representation;
- native + WebView-aware screen mapping;
- double tap and hardware key primitives;
- force-stop/app lifecycle tools;
- on-device sandboxed execution of bounded multi-step automation.

The v0.7 flow engine adopts the bounded-runtime idea but uses a strict JSON DSL instead of arbitrary JavaScript.

Source:
https://github.com/srmorete/mobile-device-mcp

### Appium MCP

Useful ideas:

- result caching;
- screenshot compression;
- normalized coordinates;
- optional visual/locator fallback;
- avoiding duplicate large UI payloads in model context.

Source:
https://github.com/appium/appium-mcp

## Design principles

### 1. Fewer round trips

The most important optimization is not adding more primitive tools. It is combining observation, synchronization and action so the agent receives useful state after every meaningful operation.

### 2. Accessibility first, screenshot second

Accessibility tree data is smaller, semantic and fast. Screenshots are used when:

- Accessibility exposes no useful nodes;
- the caller explicitly requests an image;
- later visual fallback is needed.

Screenshots must not be emitted by default after every action.

### 3. Structured operations before shell

If a capability can be represented as a typed MCP tool or flow step, that is preferred over shell. Shell backends remain available for exceptional cases.

### 4. No blind retry for mutating actions

An action may already have completed when a timeout occurs. The runtime must observe before deciding whether a retry is safe.

### 5. Local execution for deterministic sequences

Short deterministic workflows should execute on-device in one RPC rather than forcing the model through multiple network round trips.

### 6. Capability-driven routing

The runtime reports which backends are available. It does not silently escalate privileges.

## Architecture

```text
MCP Client / Agent
        |
        v
Node MCP bridge
        |
        v
Tailscale authenticated RPC
        |

Android Runtime
  +------------------------------+
  | Observation Engine           |
  | Action Engine                |
  | Synchronization Engine       |
  | Flow Runtime                 |
  | Backend Capability Router    |
  | Trace / Diagnostics          |
  +------------------------------+
        |
        +--> AccessibilityService
        +--> Android system APIs
        +--> SAF
        +--> Notification Listener
        +--> Shizuku (optional)
        +--> Termux (optional)
        +--> future ADB adapter (optional)
```

## Observation Engine

### android_screen_context

This becomes the preferred first UI tool.

Input:

```json
{
  "treeMode": "compact",
  "screenshot": false,
  "includeInvisible": false,
  "maxNodes": 250
}
```

Response:

```json
{
  "snapshotId": 41,
  "uiHash": "...",
  "packageName": "com.example.app",
  "windowClass": "...",
  "display": {
    "width": 1080,
    "height": 2400,
    "rotation": 0,
    "orientation": "portrait"
  },
  "input": {
    "keyboardVisible": true,
    "focusedEditable": true
  },
  "nodes": [],
  "truncated": false,
  "screenshot": null
}
```

The compact tree is flattened and only includes agent-relevant fields:

- stable path;
- text/content description/hint with password redaction;
- package/class/view id;
- bounds;
- clickable/editable/scrollable/focused/enabled;
- selected/checked where available.

The engine computes a canonical UI hash from sanitized semantic state, not from raw object identity.

### Snapshot cache

Keep only a small bounded in-memory snapshot ring:

- maximum 8 snapshots;
- no persistence to disk;
- sanitized tree only;
- optional screenshot is not retained unless required for immediate diff computation;
- snapshot IDs are process-local and reset after app restart.

### android_screen_diff

Input:

```json
{
  "fromSnapshotId": 40,
  "toSnapshotId": 41
}
```

Returns:

- added nodes;
- removed nodes;
- changed nodes;
- package/window change;
- focus change;
- keyboard change;
- optional changed-region metadata for screenshots when both snapshots include images.

The primary delta is semantic UI, not pixel diff.

## Synchronization Engine

### android_wait_idle

Wait until the UI is stable instead of sleeping for a fixed delay.

Stability definition:

- no relevant accessibility events for `quietMs`;
- active package/window unchanged;
- optional semantic UI hash unchanged for two consecutive samples.

Bounds:

- timeout: 0-12000 ms;
- quiet window: 100-1000 ms.

### android_wait_change

Wait until semantic state changes from a supplied snapshot/hash.

Useful after actions where the exact resulting selector is unknown.

### android_wait_activity

Wait for an exact package and optional window/activity identity where available.

### android_scroll_to

Given a semantic selector:

1. check current visible tree;
2. if found, return immediately;
3. identify a scrollable ancestor/container;
4. perform bounded scroll steps;
5. wait for UI change after each scroll;
6. stop if found, end reached, repeated UI hash detected or max steps exhausted.

No unbounded scrolling.

## Action Engine

Existing actions remain compatible.

New primitives:

- `android_double_tap`;
- `android_drag`;
- `android_pinch` with inward/outward direction and bounded scale gesture;
- `android_press_key` for enter, delete, escape/back, tab where Android supports it, DPAD directions/center, volume keys and media keys;
- `android_force_stop_app` only through an explicitly available privileged backend;
- `android_app_details` for installed package metadata and current launchability;
- `android_open_app_settings`.

Normal app launching remains an Android API operation.

## Act-and-observe loop

### android_act_and_observe

This is the core v0.7 optimization.

Input:

```json
{
  "action": {
    "method": "ui_click",
    "params": {
      "text": "Continue"
    }
  },
  "wait": {
    "mode": "idle",
    "timeoutMs": 5000
  },
  "observe": {
    "mode": "diff",
    "screenshot": false
  }
}
```

Execution:

1. capture a lightweight pre-action snapshot;
2. execute one validated action;
3. synchronize using idle/change/selector/activity policy;
4. capture a post-action snapshot;
5. return action result + new context/diff.

Output:

```json
{
  "action": {
    "ok": true
  },
  "wait": {
    "condition": "idle",
    "elapsedMs": 341
  },
  "beforeSnapshotId": 12,
  "afterSnapshotId": 13,
  "changed": true,
  "diff": {}
}
```

If the action outcome is uncertain because of timeout:

- return `outcomeUnknown: true`;
- still try a safe observation;
- never automatically repeat the action.

## Flow Runtime

### Goal

Execute deterministic multi-step UI sequences on-device with minimal network latency.

### Tool

`android_flow`

### Format

Strict JSON DSL, no JavaScript, no arbitrary reflection and no shell.

Maximum:

- 40 steps;
- 20 seconds total flow deadline;
- 12 scroll/search iterations per step;
- bounded result payload.

Supported step types:

- `find`;
- `click`;
- `set_text`;
- `tap`;
- `double_tap`;
- `long_press`;
- `swipe`;
- `scroll`;
- `scroll_to`;
- `press_key`;
- `launch_app`;
- `global_action`;
- `wait_idle`;
- `wait_change`;
- `wait_selector`;
- `assert_selector`;
- `assert_package`;
- `observe`.

Control:

- sequential steps;
- `ifPresent` / `ifAbsent` conditional guard per step;
- `onError: stop|continue`;
- named capture variables for selector matches and snapshot IDs.

No loops in v0.7 except bounded internal `scroll_to`.

This prevents arbitrary programmable infinite loops while still removing most MCP round trips.

### Flow result

Each step records:

- index;
- type;
- started/ended time;
- duration;
- status;
- error code if any;
- snapshot/hash after mutating operations when requested.

Text entered by the flow is not duplicated into the trace.

## Backend Capability Router

### android_capabilities

Reports feature availability without exposing secrets:

```json
{
  "accessibility": true,
  "notificationListener": true,
  "safRoots": 2,
  "termux": {
    "available": true,
    "authorized": true
  },
  "shizuku": {
    "available": true,
    "authorized": true,
    "mode": "shell"
  },
  "adb": {
    "available": false
  },
  "features": {
    "ui": true,
    "forceStop": true,
    "logcat": true,
    "webviewInspection": false
  }
}
```

### Routing rules

Preference order is capability-specific, not one universal escalation ladder.

Examples:

- UI click: Accessibility only;
- file read/write: SAF first;
- force stop: Shizuku if explicitly authorized, otherwise unavailable;
- shell command: caller explicitly chooses Termux or Shizuku;
- logcat: Shizuku when authorized, future ADB otherwise;
- app launch: Android API;
- notification reply: Notification Listener.

There is no silent root fallback.

## Diagnostics

### android_diagnostics

Structured diagnostic bundle:

- service state;
- foreground package/window;
- Accessibility connected;
- Notification Listener connected;
- Tailscale address/recovery state;
- recent bounded metadata-only events;
- recent flow traces;
- backend availability;
- last stable internal error codes;
- memory/snapshot cache counts.

No bearer token, SAF URI, clipboard content, notification body, entered text or shell command is included.

### Logcat

Full logcat is not a standard unprivileged feature.

When Shizuku is explicitly authorized, add a structured `android_logcat` tool:

- line count/time range bounded;
- optional package/pid/tag filter;
- redact obvious bearer-token patterns;
- maximum response bytes.

Future ADB backend can implement the same tool interface.

## WebView strategy

WebView is not required for the first v0.7 milestone.

Phase 1:

- detect WebView-like nodes/classes;
- report `webViewDetected` in screen context;
- continue Accessibility-based interaction.

Phase 2, only if technically justified:

- optional Chrome DevTools Protocol bridge for debuggable WebViews;
- never assume arbitrary production apps expose a debug socket;
- no weakening of app security settings.

## Optional visual fallback

The runtime does not embed a vision model.

It prepares efficient primitives for an external agent/vision model:

- compressed screenshot option;
- normalized coordinates 0-1000 in addition to absolute coordinates;
- semantic context paired with image geometry;
- image capture only when requested or Accessibility is insufficient.

A future visual locator can be added as a separate optional layer.

## Coordinate model

All coordinate actions continue accepting absolute pixels for compatibility.

New actions also accept optional normalized coordinates:

- x/y range 0-1000;
- converted using current display dimensions at execution time.

This makes image-model coordinates independent of phone resolution.

## App profiles

Profiles are hints, not privileged automations.

An optional profile can define:

- known package name;
- preferred selectors;
- common screen identifiers;
- safe synchronization hints.

Profiles must never contain credentials or bypass permissions.

Profiles are not part of the first v0.7 implementation milestone unless needed to validate the architecture.

## Tool discovery

The project already has a manageable tool count, but v0.7 adds grouped capability metadata to help agents choose efficiently.

`android_capabilities` returns:

- tool categories;
- required permissions/backend;
- whether the operation is read-only, mutating, destructive or outcome-uncertain;
- availability at runtime.

A separate fuzzy `tool_search` tool is deferred unless the MCP tool count grows enough to justify it.

## Performance targets

These are local architecture targets, not claims against other projects:

- `screen_context` without screenshot: target <100 ms on a typical device;
- action + idle + diff: usually one network round trip;
- compact tree payload: target at least 40% smaller than current full `ui_tree` on common screens;
- no screenshot base64 in model context unless requested;
- flow of 5 deterministic steps should require one MCP call instead of 5-15 calls.

## Safety model

Existing boundaries remain:

- user explicitly starts remote service;
- Tailscale-only bind;
- 256-bit bearer token;
- locked screen blocks UI actions;
- password nodes redacted;
- SAF paths stay under explicit user roots;
- Notification Listener permission explicit;
- Shizuku and Termux permission explicit;
- no silent privilege escalation;
- no PIN/biometric bypass;
- no protected-window bypass.

Additional v0.7 rules:

- flow DSL cannot invoke shell;
- flow DSL cannot mutate SAF files;
- flow has fixed step/deadline limits;
- destructive privileged actions remain separate named tools;
- mutating actions are not blindly retried;
- trace data excludes sensitive content;
- screen snapshots are bounded and memory-only.

## Versioning and compatibility

Target release: v0.7.0.

Existing 47 MCP tools remain backward compatible where practical.

New tools are additive.

The existing `android_batch` remains temporarily for compatibility but becomes secondary to `android_flow` and may later be deprecated.

## Implementation milestones

### Milestone A — Smart loop core

- compact screen context;
- semantic snapshots/hash;
- screen diff;
- wait idle/change;
- act-and-observe;
- scroll-to;
- normalized coordinates.

### Milestone B — Flow runtime

- strict flow schema;
- local execution;
- conditional guards;
- trace output;
- flow tests and deadline enforcement.

### Milestone C — Device-control expansion

- double tap;
- drag;
- pinch;
- key press;
- app details/settings;
- explicit privileged force-stop;
- capabilities;
- diagnostics;
- bounded logcat through Shizuku.

### Milestone D — Optional advanced surfaces

- WebView detection;
- screenshot compression/diff optimization;
- external visual fallback hooks;
- app profiles if evidence shows they improve reliability.

ADB remains a separate future optional adapter rather than a v0.7 requirement.

## Test strategy

Pure-Java tests:

- canonical snapshot hashing;
- semantic diff;
- idle detector;
- flow schema validation;
- flow step/deadline limits;
- conditional flow execution;
- capability routing decisions;
- normalized coordinate conversion;
- sensitive trace redaction.

Android JVM/integration-level tests where possible:

- screen context encoding;
- selector behavior;
- action-and-observe orchestration;
- diagnostics encoding.

Node tests:

- new MCP schemas;
- malformed flow rejection before phone RPC;
- structured image/context handling;
- backward-compatible 47 existing tools;
- tool count/version consistency.

Final gate:

```powershell
npm.cmd run check
./build-android.ps1
git diff --check
```

Physical-phone acceptance:

- context reflects actual current app/focus/keyboard;
- click + observe reaches stable next screen;
- scroll-to finds an initially off-screen element;
- flow executes deterministic 5+ step navigation;
- Tailscale reconnect during flow fails safely rather than repeating actions;
- Shizuku force-stop/logcat work only after explicit authorization;
- screenshot is not transferred unless requested.

## Non-goals for v0.7

- universal bypass of Android security boundaries;
- silent APK installation;
- automatic root/Shizuku escalation;
- arbitrary JavaScript execution on the phone;
- arbitrary shell inside flows;
- always-on screen recording;
- storing UI/screenshot history to disk;
- complete WebView/CDP support for all apps;
- mandatory ADB.
